# Art Design Pro 前端二次开发计划

## 1. 目标

基于 `Daymychen/art-design-pro` 评估并规划新的前端二次开发基座，逐步替换当前 `frontend` 中的 Naive UI 管理端实现，同时保留本项目已有后端能力、权限模型、菜单初始化数据和代码生成链路。

本计划只定义迁移路径和实施边界，不直接修改现有前端运行代码。

## 2. 当前项目现状

当前仓库是前后端一体后台管理系统：

- 后端：Java 17、Spring Boot 3.2.0、Maven 多模块、MyBatis-Plus、Sa-Token。
- 前端：Vue 3、TypeScript、Vite、Naive UI、UnoCSS、Pinia、Vue Router、Axios。
- 前端目录：`frontend`。
- API 封装目录：`frontend/src/service`。
- 路由目录：`frontend/src/router`。
- 权限和菜单初始化数据：后端代码、`service.sql`、前端路由共同约束。
- 代码生成器：`service-code-generate`，生成模板与当前前端组件体系有关。

## 3. 目标基座评估

`art-design-pro` 技术栈：

- Vue 3
- TypeScript
- Vite 7
- Element Plus
- Tailwind CSS 4
- Pinia
- Vue Router
- Axios
- vue-i18n
- ECharts
- WangEditor

适合复用的能力：

- 登录页和认证流程骨架。
- 动态菜单、动态路由、路由守卫。
- 工作标签页。
- 主题、暗黑模式、布局配置。
- 常见后台页面组件和交互风格。
- 表格、表单、图表、富文本、异常页等示例资产。

需要重点适配的能力：

- HTTP 响应结构。
- Token 请求头格式。
- 后端菜单字段与前端动态路由字段。
- 按钮权限和页面权限。
- 现有代码生成模板。
- 现有业务页面从 Naive UI 到 Element Plus 的组件迁移。

## 4. 总体策略

采用“新基座分支验证、核心链路先跑通、业务页面分批迁移”的方式推进。

不建议在当前 `frontend` 目录内直接混用 Naive UI 和 Element Plus 长期开发。短期验证可以并存，正式迁移时应明确一个目标 UI 体系，避免样式、表单校验、弹窗、表格封装和主题变量长期双轨。

推荐策略：

1. 在独立迁移分支中引入 `art-design-pro` 基座。
2. 先跑通登录、用户信息、菜单权限三个核心链路。
3. 再迁移系统管理页面。
4. 最后调整代码生成器模板，使后续生成代码面向新前端基座。

## 5. 分阶段计划

### 阶段一：基座验证

目标：确认 `art-design-pro` 能在本项目开发环境中稳定运行。

任务：

- 拉取 `art-design-pro` 到临时目录或独立分支。
- 确认 Node、pnpm 版本满足要求。
- 执行依赖安装、开发启动和生产构建。
- 清理 demo 页面，保留布局、登录、路由、权限、异常页、基础组件。
- 记录需要保留和删除的目录清单。

验收：

- 本地可以启动。
- 生产构建通过。
- 删除 demo 页面后路由不报错。
- 登录页、基础布局、菜单、标签页、异常页可访问。

### 阶段二：后端认证对接

目标：让新前端使用当前后端完成登录和用户信息获取。

任务：

- 适配登录接口。
- 适配用户信息接口。
- 适配退出登录接口。
- 统一 Token 存储和请求头注入方式。
- 统一 401 处理和登录过期跳转。
- 统一后端响应结构。

重点文件：

- `src/api/auth.ts`
- `src/utils/http/index.ts`
- `src/store/modules/user.ts`
- `src/router/guards/beforeEach.ts`

验收：

- 使用真实账号可以登录。
- 刷新页面后登录态可恢复。
- Token 失效后可自动退出到登录页。
- 登录接口错误能显示明确提示。

### 阶段三：菜单和权限对接

目标：使用当前后端菜单、角色、权限数据驱动前端路由。

任务：

- 梳理当前后端菜单字段。
- 对齐 `art-design-pro` 动态路由字段。
- 适配菜单树转换逻辑。
- 适配按钮权限标识。
- 检查 `service.sql` 中系统菜单初始化数据。
- 确认前端路由 path、name、component 与数据库菜单一致。

重点文件：

- `src/router/core/MenuProcessor.ts`
- `src/router/core/RouteRegistry.ts`
- `src/router/core/RouteTransformer.ts`
- `src/router/core/RoutePermissionValidator.ts`
- `src/store/modules/menu.ts`
- `service.sql`

验收：

- 不同角色登录后菜单不同。
- 无权限页面不能访问。
- 刷新动态路由页面不 404。
- 菜单折叠、标签页、面包屑保持正常。
- 按钮权限可以控制新增、编辑、删除等操作。

### 阶段四：系统管理页面迁移

目标：优先迁移后台必需页面，形成业务页面开发范式。

优先顺序：

1. 登录页。
2. 首页。
3. 用户管理。
4. 角色管理。
5. 菜单管理。
6. 字典或参数配置。
7. 代码生成相关页面。

任务：

- 将当前 Naive UI 页面迁移为 Element Plus 页面。
- 统一列表页结构、搜索栏、表格、分页、弹窗表单、删除确认。
- 统一 loading、empty、error、success message。
- 抽取项目内通用页面模式。

验收：

- 系统管理主链路可完成增删改查。
- 表单校验和后端校验错误均能反馈到用户。
- 表格分页、搜索、重置、刷新可用。
- 移动端或窄屏下不出现明显布局错乱。

### 阶段五：代码生成器适配

目标：让代码生成器生成的新页面符合新前端基座。

任务：

- 检查 `service-code-generate` 中前端模板。
- 将模板组件从 Naive UI 改为 Element Plus。
- 将 API 调用路径改为新基座约定。
- 将列表、表单、弹窗、权限按钮模板统一。
- 生成一个测试模块并验证前后端联动。

验收：

- 生成页面可以直接编译。
- 生成接口封装符合新项目结构。
- 生成菜单和权限标识可与后端初始化数据联动。
- 生成页面至少完成一个 CRUD 流程验证。

### 阶段六：正式替换与收口

目标：替换旧前端并收敛工程文档。

任务：

- 确定旧 `frontend` 保留、备份或替换策略。
- 更新 README 中前端技术栈和运行说明。
- 更新 AGENTS.md 中前端开发规则。
- 清理无用依赖、静态资源、旧 UI 组件封装。
- 补充开发规范文档。

验收：

- `pnpm install`、`pnpm run dev`、`pnpm run build` 正常。
- README 与实际技术栈一致。
- 新增页面有明确目录和代码规范。
- 无旧 UI 体系残留依赖，或残留项有明确说明。

## 6. 关键接口适配清单

需要优先确认当前后端接口：

- 登录接口。
- 登出接口。
- 当前用户信息接口。
- 当前用户菜单接口。
- 当前用户按钮权限接口。
- 验证码接口，如保留验证码。
- 文件上传接口，如系统管理页面用到头像或附件。

需要统一的数据结构：

- 成功响应结构。
- 失败响应结构。
- 分页响应结构。
- 菜单节点结构。
- 用户信息结构。
- 权限标识结构。

## 7. 风险和处理方式

### UI 体系切换风险

当前前端是 Naive UI，目标基座是 Element Plus。两个组件库的表单、表格、弹窗、消息提示、主题变量差异较大。

处理方式：

- 正式迁移后不要长期双 UI 体系。
- 先迁移系统管理页面作为范式。
- 通用业务组件在新基座中重新抽象。

### 菜单协议不一致风险

动态菜单是后台系统最容易出问题的环节。字段不一致会导致刷新 404、菜单丢失、权限绕过或无权限误判。

处理方式：

- 先固定后端菜单字段。
- 再写转换器适配前端路由。
- 每次改菜单结构同步检查 `service.sql`。

### 代码生成器失配风险

当前代码生成器可能仍按旧前端生成 Naive UI 页面。

处理方式：

- 新基座核心链路跑通后立即改生成模板。
- 不要等业务页面大量迁移后再处理生成器。

### 构建环境升级风险

`art-design-pro` 依赖较新，Node 和 pnpm 版本要求高于当前老模板常见环境。

处理方式：

- 在 README 中写明 Node 和 pnpm 版本。
- CI 或部署环境同步升级。
- 本地优先使用固定版本管理。

## 9. 推荐下一步

下一步建议新建专门迁移分支，例如 `feat/art-design-pro-frontend`，先只完成 M1 和 M2。

不要一开始就整体替换全部业务页面。先用登录、用户信息、菜单权限验证基座与当前后端是否匹配，再决定是否全面迁移。
